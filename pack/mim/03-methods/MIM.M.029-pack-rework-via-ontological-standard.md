# MIM.M.029 — Pack rework через онтологический стандарт

## Описание

Rework существующего Pack-знания = применение канонического онтологического стандарта (BORO, UFO, DOLCE, 4D) к уже описанным сущностям. Не переписывание содержания, а formal grounding задним числом: существующие методы/различения/SOTA получают онтологическую базу через стандарт.

## Вход

- Pack с N ad-hoc сущностями (методы, различения без явной онтологической основы)
- Выбранный онтологический стандарт (BORO / UFO / DOLCE / 4D)

## Выход

- Cross-pack alignment: сущности нескольких связанных Pack получают согласованную онтологическую базу
- `trust: hypothesis` + `revision_criterion` на каждой переоформленной сущности
- SOTA-аннотация эволюции парадигм (опционально)

## Алгоритм

1. Выбрать стандарт — критерий: покрывает ли парадигмы, использованные в Pack (Substance/Entity/Object для BORO)?
2. Sweep existing entities — список ad-hoc формализаций
3. Map: каждой сущности — категория стандарта (Object/Type/Tuple/...)
4. Refactor in-place — frontmatter + body содержат категорию + revision_criterion
5. Cross-pack alignment — связанные Pack (personal, digital-platform) обновить синхронно
6. Add SOTA-annotation paradigm-history (если стандарт сам — эволюция)

## Forces

_(Optional, WP-448 Ф10) Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Формальный grounding ↔ переписывание содержания | Метод явно определён как «не переписывание содержания, а formal grounding задним числом», но на практике трудно map существующую ad-hoc сущность в категорию стандарта, вообще не тронув формулировку — граница между переоформлением и переписыванием размывается в процессе |
| Cross-pack alignment ↔ автономность каждого Pack | Шаг 5 требует синхронно обновлять связанные Pack, но каждый Pack имеет собственный темп развития и владельца — синхронизация ради согласованной онтологической базы противоречит независимости эволюции отдельных Pack |
| Единый онтологический стандарт ↔ разнообразие уже накопленных парадигм | Шаг 1 требует выбрать стандарт, покрывающий использованные в Pack парадигмы, но mature Pack с 30+ ad-hoc сущностями почти наверняка содержит смесь парадигм, накопленных за время развития — один стандарт неизбежно будет более естественным для одних сущностей, чем для других |

## Bias-Annotation _(tentative — trust: hypothesis, единственный прецедент WP-345 Ф-B)_

_(Optional, WP-448 Ф10) Какое систематическое искажение грозит практикующему._

| Bias | Direction of distortion |
|------|--------------------------|
| Rework подменяется переименованием без реального grounding | Под давлением объёма (30+ сущностей) шаг 3 (map каждой сущности в категорию стандарта) рискует свестись к механической подстановке нового термина вместо термина старого — именно это Failure mode прямо называет: «rework сводится к переписыванию имён, не к grounding» |
| Cross-pack alignment выполняется избирательно, самый трудный Pack откладывается | Синхронизация нескольких связанных Pack (шаг 5) требует равного внимания ко всем, но естественно начинать с Pack, где refactor даётся легче — сложный или спорный случай откладывается «на потом», и cross-pack drift частично воспроизводится внутри самого rework |

## Критерий применимости

«Есть ли в Pack сущность, описанная ad-hoc, без явной онтологической базы?» Да → кандидат на rework. Особенно полезно при cross-pack drift, когда родственные Pack описывают одну онтологическую территорию через несовместимые понятия.

## Failure mode без метода

Ad-hoc Pack-сущности накапливают drift: один Pack использует «Object», другой «Сущность», третий «Концепт» — без формального соответствия. При cross-pack reasoning возникает confusion. Без онтологического стандарта rework сводится к переписыванию имён, не к grounding.

## Применимо к

- Mature Pack'и с ≥30 ad-hoc сущностями
- Cross-pack alignment (≥2 связанных Pack)
- Подготовка Pack к публикации (внешний reader нуждается в онтологической базе)
